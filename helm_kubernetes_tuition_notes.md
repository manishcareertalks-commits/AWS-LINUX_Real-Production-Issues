# Helm — Kubernetes Package Manager

## 1. What is Helm?

**Helm is a package manager for Kubernetes.**

When deploying an application on Kubernetes, we may need multiple Kubernetes objects:

- Pod
- Deployment
- Service
- ConfigMap
- Ingress
- Namespace
- Secret
- HPA
- etc.

Each object can have its own YAML manifest.

For example:

```text
manifests/
├── namespace.yaml
├── deployment.yaml
├── service.yaml
├── configmap.yaml
└── ingress.yaml
```

These can be deployed using:

```bash
kubectl apply -f ./manifests/
```

This works, but managing many manifests can become difficult when the application needs to be:

- Reused across environments
- Configured with different values
- Versioned
- Packaged and distributed
- Installed and upgraded consistently
- Rolled back when required

**Helm solves this problem by packaging Kubernetes application definitions into a reusable unit called a Helm Chart.**

---

# 2. What is a Helm Chart?

A **Helm Chart** is a package containing everything required to define and deploy a Kubernetes application.

A chart can contain:

- Kubernetes resource templates
- Default configuration values
- Chart metadata
- Dependencies
- Reusable template helpers
- Installation notes

Think of it as:

```text
Helm Chart
    │
    ├── Templates
    ├── Configuration
    ├── Metadata
    └── Dependencies
```

The chart is the package.

Helm uses the chart and its configuration values to generate Kubernetes manifests.

---

# 3. Creating a Helm Chart

The `helm create` command creates a starter Helm Chart.

```bash
helm create myapp
```

This creates a directory similar to:

```text
myapp/
│
├── Chart.yaml
├── values.yaml
├── charts/
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── _helpers.tpl
│   ├── NOTES.txt
│   └── ...
│
└── .helmignore
```

> The exact files generated by `helm create` can vary slightly depending on the Helm version and chart template.

---

# 4. Helm Chart Directory Structure

## `Chart.yaml`

`Chart.yaml` contains the **metadata of the Helm Chart**.

Typical information includes:

```yaml
apiVersion: v2
name: myapp
description: A Helm chart for Kubernetes
type: application
version: 0.1.0
appVersion: "1.0.0"
```

### Important fields

| Field | Purpose |
|---|---|
| `apiVersion` | Chart API version |
| `name` | Name of the chart |
| `description` | Description of the chart |
| `type` | Chart type, usually `application` |
| `version` | Version of the Helm Chart |
| `appVersion` | Version of the application |

### Important distinction

```text
version     → Helm Chart version
appVersion  → Application version
```

They can be different.

---

# 5. `values.yaml`

`values.yaml` contains the **default configuration values** used by the chart templates.

Example:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"
```

A template can reference these values.

For example:

```yaml
replicas: {{ .Values.replicaCount }}
```

If:

```yaml
replicaCount: 2
```

the rendered Kubernetes manifest will contain:

```yaml
replicas: 2
```

### Why is `values.yaml` important?

It allows the same chart to be reused with different configurations.

For example:

### Development

```yaml
replicaCount: 1

image:
  repository: nginx
  tag: "1.27"
```

### Production

```yaml
replicaCount: 5

image:
  repository: nginx
  tag: "1.28"
```

The Kubernetes templates can remain the same while configuration changes through values.

---

# 6. `templates/`

The `templates/` directory contains the **Kubernetes resource templates**.

Common templates include:

```text
templates/
├── deployment.yaml
├── service.yaml
├── ingress.yaml
├── configmap.yaml
└── _helpers.tpl
```

These files look like Kubernetes YAML, but they can contain **Helm template expressions**.

For example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
```

Here:

```text
.Values.replicaCount
```

reads the value from:

```yaml
values.yaml
```

---

# 7. Why Use Templates?

Without Helm, a manifest might contain:

```yaml
replicas: 2
```

This value is hardcoded.

With Helm:

```yaml
replicas: {{ .Values.replicaCount }}
```

and:

```yaml
replicaCount: 2
```

The value becomes configurable.

For another environment, the value can be changed without modifying the Kubernetes template.

This is one of the key reasons Helm Charts are **reusable and configurable**.

---

# 8. Helm Template Syntax

Helm uses the Go template language.

A common expression is:

```yaml
{{ .Values.replicaCount }}
```

Meaning:

```text
.Values
    ↓
values.yaml

.replicaCount
    ↓
replicaCount value
```

Example:

### `values.yaml`

```yaml
replicaCount: 3
```

### Template

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

### Rendered manifest

```yaml
spec:
  replicas: 3
```

---

# 9. `deployment.yaml`

A Helm `deployment.yaml` template can define the Kubernetes Deployment.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ include "myapp.name" . }}
  template:
    metadata:
      labels:
        app: {{ include "myapp.name" . }}
    spec:
      containers:
        - name: myapp
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Notice that the image and replica count are configurable.

---

# 10. `service.yaml`

`service.yaml` can define the Kubernetes Service.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  selector:
    app: {{ include "myapp.name" . }}
  ports:
    - port: 80
      targetPort: 80
```

The Service connects network traffic to the Pods created by the Deployment.

---

# 11. `ingress.yaml`

`ingress.yaml` can define an Ingress resource.

For example:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  rules:
    - host: myapp.example.com
```

Ingress configuration can also be made configurable through `values.yaml`.

---

# 12. `_helpers.tpl`

`_helpers.tpl` contains **reusable Helm template helpers**.

It is commonly used for:

- Common names
- Labels
- Selectors
- Naming conventions
- Reusable template logic

Example:

```yaml
{{- define "myapp.name" -}}
myapp
{{- end }}
```

The helper can then be reused:

```yaml
name: {{ include "myapp.name" . }}
```

### Why use helpers?

Instead of repeating the same template logic across multiple files, define it once and reuse it.

---

# 13. `charts/`

The `charts/` directory is used for **chart dependencies or subcharts**.

A Helm application can depend on other charts.

For example:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── charts/
│   └── database/
└── templates/
```

The dependency relationship can also be declared in `Chart.yaml`.

Example:

```yaml
dependencies:
  - name: redis
    version: "20.x.x"
    repository: "https://example.com/charts"
```

Helm can then manage the dependency as part of the chart.

---

# 14. `NOTES.txt`

`NOTES.txt` contains information that Helm can display after installation.

For example:

```text
1. Get the application URL by running:

   kubectl get svc myapp
```

After installing a chart, Helm can display these notes to help users understand how to access or use the deployed application.

---

# 15. `.helmignore`

`.helmignore` works similarly to `.gitignore`.

It specifies files that should be excluded when Helm packages the chart.

Example:

```text
.git/
.gitignore
README.md
*.tmp
```

The purpose is to prevent unnecessary files from being included in the packaged chart.

---

# 16. How Helm Works

The overall flow can be understood as:

```text
values.yaml
     │
     ▼
Helm Templates
     │
     ▼
Rendered Kubernetes Manifests
     │
     ▼
Kubernetes API Server
     │
     ▼
Kubernetes Resources
```

For example:

```text
values.yaml
replicaCount: 3
image:
  repository: nginx
  tag: "1.27"
       │
       ▼
templates/deployment.yaml
       │
       ▼
Helm renders the template
       │
       ▼
Deployment manifest
replicas: 3
image: nginx:1.27
       │
       ▼
Kubernetes API Server
       │
       ▼
Deployment → ReplicaSets → Pods
```

# 17. Helm Rendering

Helm can render templates locally without installing anything into the cluster.

Use:

```bash
helm template myapp ./myapp
```

This generates the Kubernetes manifests from the Helm templates.

This is useful for checking what Kubernetes YAML Helm will produce.

---

# 18. Validate a Helm Chart

Use:

```bash
helm lint ./myapp
```

`helm lint` checks the chart for common issues.

Example:

```bash
helm lint ./myapp
```

A successful linting process helps identify chart problems before installation.

---

# 19. Install a Helm Chart

A chart can be installed using:

```bash
helm install myapp ./myapp
```

Here:

```text
myapp       → Release name
./myapp     → Chart location
```

A successful installation creates a **Helm Release**.

---

# 20. Helm Release

A **Release** is an installed instance of a Helm Chart.

The same chart can be installed multiple times with different release names.

Example:

```bash
helm install myapp-dev ./myapp
helm install myapp-prod ./myapp
```

Conceptually:

```text
                 Helm Chart
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     myapp-dev              myapp-prod
       Release                 Release
```

The chart is the package.

The release is a deployed instance of that package.

---

# 21. Override `values.yaml`

The default `values.yaml` can be overridden during installation.

Example:

```bash
helm install myapp ./myapp \
  --set replicaCount=5
```

This overrides:

```yaml
replicaCount: 2
```

with:

```yaml
replicaCount: 5
```

---

# 22. Using a Custom Values File

Instead of using `--set`, a separate values file can be supplied.

Example:

```text
values.yaml
values-dev.yaml
values-prod.yaml
```

Production:

```bash
helm install myapp ./myapp \
  -f values-prod.yaml
```

Development:

```bash
helm install myapp ./myapp \
  -f values-dev.yaml
```

This allows the same chart to be used across multiple environments.

---

# 23. Upgrade a Helm Release

When the chart or configuration changes:

```bash
helm upgrade myapp ./myapp
```

With a custom values file:

```bash
helm upgrade myapp ./myapp \
  -f values-prod.yaml
```

The existing release is updated with the new chart configuration.

---

# 24. Rollback a Helm Release

Helm keeps release history.

View the history:

```bash
helm history myapp
```

Rollback to a previous revision:

```bash
helm rollback myapp 1
```

This is useful when a deployment needs to be reverted to an earlier release revision.

---

# 25. List Helm Releases

To see releases:

```bash
helm list
```

For all namespaces:

```bash
helm list -A
```

---

# 26. Check Release Status

```bash
helm status myapp
```

This provides information about the current state of the Helm release.

---

# 27. Uninstall a Release

To remove a Helm release:

```bash
helm uninstall myapp
```

This removes the Kubernetes resources managed by that release.

# 29. Helm Chart vs Kubernetes Manifest

| Kubernetes Manifests | Helm Chart |
|---|---|
| Individual YAML files | Packaged application definition |
| Values often hardcoded | Configuration can be externalized |
| Manual organization | Standard chart structure |
| Reuse requires more manual work | Designed for reuse |
| No built-in release history | Helm tracks releases |
| `kubectl apply` commonly used | `helm install` / `helm upgrade` commonly used |
| Rollback requires managing manifests/versioning separately | Helm provides release rollback |

---

# 30. Helm vs `kubectl apply -f`

### Using Kubernetes manifests

```bash
kubectl apply -f ./manifests/
```

This directly applies the YAML files to Kubernetes.

### Using Helm

```bash
helm install myapp ./myapp
```

Helm processes the chart templates and values, produces the Kubernetes resource definitions, and manages the resulting release.

### Key difference

```text
kubectl
   │
   └── Applies Kubernetes manifests

Helm
   │
   ├── Chart
   ├── Values
   ├── Templates
   └── Release management
```

Helm does not replace Kubernetes.

**Helm is a tool that helps package, configure, install, upgrade, and manage Kubernetes applications.**

# 31. Important Concept: Chart vs Release

This is a common interview question.

### Chart

The reusable package.

```text
myapp/
├── Chart.yaml
├── values.yaml
└── templates/
```

### Release

A deployed instance of that chart.

```text
helm install myapp-dev ./myapp
```

Here:

```text
Chart  → ./myapp
Release → myapp-dev
```

The same chart can create multiple releases.

---

# 32. Important Concept: `values.yaml` vs Templates

### `values.yaml`

Contains configuration:

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: "1.27"
```

### Template

Consumes that configuration:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}

  containers:
    - image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

### Result

```yaml
spec:
  replicas: 3

  containers:
    - image: "nginx:1.27"
```

So remember:

```text
values.yaml
     ↓
Configuration

templates/
     ↓
How Kubernetes resources should be generated
```

# 34. Practical Helm Workflow

A typical workflow can look like this:

### Step 1 — Create the chart

```bash
helm create myapp
```

### Step 2 — Configure values

Edit:

```text
values.yaml
```

### Step 3 — Create or modify templates

Edit:

```text
templates/
```

### Step 4 — Validate the chart

```bash
helm lint ./myapp
```

### Step 5 — Render the templates

```bash
helm template myapp ./myapp
```

### Step 6 — Install

```bash
helm install myapp ./myapp
```

### Step 7 — Verify

```bash
helm status myapp
kubectl get pods
kubectl get svc
```

### Step 8 — Make changes

Update:

```text
values.yaml
```

or the templates.

### Step 9 — Upgrade

```bash
helm upgrade myapp ./myapp
```

### Step 10 — Roll back if required

```bash
helm history myapp
helm rollback myapp <REVISION>
```

# 35. Interview Scenario

### Interviewer

> You need to deploy an application that contains a Deployment, Service, ConfigMap, and Ingress. How would you manage this using Helm?

### Answer

First, create a Helm Chart:

```bash
helm create myapp
```

Then define the Kubernetes resources as templates inside:

```text
templates/
```

For example:

```text
deployment.yaml
service.yaml
configmap.yaml
ingress.yaml
```

The configurable values such as replica count, image repository, image tag, and service configuration can be defined in:

```text
values.yaml
```

The templates reference these values using Helm template expressions such as:

```yaml
{{ .Values.replicaCount }}
```

Before deploying, validate and render the chart:

```bash
helm lint ./myapp
helm template myapp ./myapp
```

Then install it:

```bash
helm install myapp ./myapp
```

For future changes:

```bash
helm upgrade myapp ./myapp
```

And if a previous version needs to be restored:

```bash
helm history myapp
helm rollback myapp <REVISION>
```
